# UI Standards for ProdMind-Studio

## 0. 适用范围与强制级别
- 适用对象：
  - `apps/web` 的信息架构、页面布局、组件交互、视觉系统。
  - `apps/cli` 的信息层级、状态反馈、错误与重试表达。
- 强制级别：
  - `MUST`：必须执行，UI 评审不通过则不能合并。
  - `SHOULD`：强建议，偏离需在 PR 描述说明理由与替代方案。
  - `MUST NOT`：禁止项，出现即驳回。

## 1. 设计原则

## 1.1 统一风格目标
- `MUST`：体现“专业、现代、克制、未来感”四要素。
- `MUST`：界面默认围绕“状态流转 + 资产沉淀”组织，不围绕“聊天泡泡数量”组织。
- `MUST`：同一语义在全站保持同样视觉编码（例如风险、冲突、待验证、已沉淀）。

## 1.2 四个风格词的工程定义
- 专业（Professional）：
  - `MUST`：关键判断可追溯到具体阶段、输入与输出。
  - `MUST`：显示“来源、时间、状态、责任对象（engine/agent/user）”四类元信息。
- 现代（Modern）：
  - `MUST`：采用分层信息架构与语义化组件，而非纯装饰型视觉。
  - `MUST`：交互反馈具备实时性（处理中、等待输入、部分失败）。
- 克制（Restrained）：
  - `MUST NOT`：使用高饱和多色并行表达多个次要状态。
  - `MUST`：一屏只允许一个主行动按钮焦点。
- 未来感（AI Workflow Feel）：
  - `MUST`：阶段执行、模型动作、产物沉淀有明确流程可视化。
  - `SHOULD`：通过时间线、阶段条、事件日志表达“系统正在推进”。

## 1.3 信息密度与可读性平衡
- `MUST`：每个工作页面同时满足三类信息可见：
  - 当前阶段状态（现在在做什么）
  - 当前核心对象（正在分析什么）
  - 下一步可执行动作（用户能做什么）
- `MUST`：长文本区必须有结构锚点（标题、标签、分段、折叠）。
- `MUST NOT`：把高密度信息直接堆叠成连续段落或连续聊天消息。

## 1.4 结构优先 vs 对话优先
- 结构优先（`MUST` 采用）场景：
  - 决策评审、风险复核、快照对比、资产导出前校验。
  - 标准布局：结构区 >= 对话区宽度。
- 对话优先（`MUST` 采用）场景：
  - Challenge 回合进行中、需要用户即时回应冲突规则时。
  - 标准布局：对话区 > 结构区，但结构区不可隐藏为 0。
- `MUST`：任何会话页都不能只有对话，没有结构面板。

## 1.5 组件选择规则
- 卡片（Card）：
  - 用于独立对象摘要（会话、假设、风险、产物）。
- 列表（List/Table）：
  - 用于可排序可筛选集合（项目、会话、资产索引）。
- 时间线（Timeline）：
  - 用于阶段推进与快照演进。
- 树（Tree）：
  - 用于决策状态树、假设-风险关联层级。
- 状态标签（Status Tag）：
  - 用于离散状态（unvalidated/validated/rejected 等）。
- Diff 视图：
  - 用于快照、资产版本、决策变化比较。
- `MUST NOT`：用纯聊天消息承载本该结构化显示的树、列表、diff。

## 2. 信息架构原则

## 2.1 页面层级建议（Web）
- 一级：
  - 首页（Workspace Dashboard）
  - 项目页（Project）
  - 会话页（Session）
  - 资产页（Assets）
  - 决策页（Decision Review）
  - 快照页（Snapshots）
- 建议路径（可调整，但语义不变）：
  - `/`
  - `/projects/:projectId`
  - `/projects/:projectId/sessions/:sessionId`
  - `/projects/:projectId/assets`
  - `/projects/:projectId/decisions`
  - `/projects/:projectId/snapshots`

## 2.2 Challenge / Decision / Asset 的界面呈现
- Challenge：
  - 主体是回合进度 + 冲突规则触发 + 用户回应窗口。
- Decision：
  - 主体是状态树 + 假设/风险 + 置信度变化 + 调度结果。
- Asset：
  - 主体是文档资产、研究记录、导出结果与版本差异。
- `MUST`：三类能力在同一项目下形成连续链路，不是三个孤立工具页。

## 2.3 对话视图与结构视图并存规则
- `MUST`：会话页至少双栏并存：
  - 左/中：对话与阶段流
  - 右：结构化对象（假设、风险、结论、待验证、资产草稿）
- `MUST`：点击结构项可定位到对话来源段（traceback）。
- `MUST`：点击对话中的关键结论可跳转到结构面板对应条目。

## 2.4 避免做成普通聊天壳
- `MUST`：会话页保留“阶段状态条 + 结构对象区 + 产物区”三件套。
- `MUST NOT`：把“导出资产”隐藏为聊天里的自然语言命令。
- `MUST`：每轮结束后系统应显式展示“新增或变更的结构对象”。

## 3. 组件与交互规范

## 3.1 页面布局规范
- 模板 A：Explorer（首页/列表页）
  - 顶部全局导航 + 主内容列表 + 右侧筛选或统计。
- 模板 B：Workbench（会话页）
  - 顶部状态条 + 三栏（结构/对话/快照）或双栏（移动端折叠）。
- 模板 C：Review（资产/决策/快照）
  - 顶部上下文 + 主体 diff/timeline + 次级动作区。

## 3.2 顶部导航、侧栏、面包屑、标签页、二级操作区
- 顶部导航：
  - `MUST`：包含当前项目上下文、全局搜索/命令入口、主导航切换。
- 侧边栏：
  - `MUST`：用于跨页面实体切换（项目、会话、资产类别）。
- 面包屑：
  - `MUST`：展示 `Workspace > Project > Session/Asset/Snapshot`。
- 标签页（Tabs）：
  - `SHOULD`：用于同级视角切换（Overview/Timeline/Diff/Raw）。
- 二级操作区：
  - `MUST`：放置当前页面动作（重试、标记验证、生成资产、导出）。
  - `MUST NOT`：把二级动作散落在页面多个角落。

## 3.3 关键组件使用场景
- Card：
  - 会话摘要、假设项、风险项、资产项。
- Table：
  - 大量可比对象（会话列表、资产列表、测试结果列表）。
- Tree：
  - 决策状态分解、问题定义版本演进层级。
- Diff：
  - 快照对比、文档版本对比。
- Timeline：
  - 多阶段执行、快照时间序列、回合历史。
- Drawer：
  - 快速查看详情，保留上下文。
- Modal：
  - 破坏性动作确认、不可逆操作说明。
- Command Palette：
  - 高频跨页动作（跳转项目、打开会话、触发重跑、导出）。
- `MUST NOT`：将复杂流程放进单个 Modal 完成。

## 3.4 长任务 / AI 推理 / 生成中反馈
- `MUST`：任务状态至少包含：
  - queued
  - running
  - waiting_user
  - completed
  - partial_failed
  - failed
  - cancelled
- `MUST`：running 状态显示“当前阶段 + 已完成阶段 + 下一阶段”。
- `MUST`：partial_failed 显示失败子步骤与可重试粒度（全量重试/单步骤重试）。
- `MUST NOT`：只显示一个无语义的 loading spinner 超过 3 秒。

## 3.5 错误、重试、空状态、加载、部分失败
- 错误：
  - `MUST`：包含错误类型、影响范围、建议动作。
- 重试：
  - `MUST`：提供明确重试入口与幂等提示。
- 空状态：
  - `MUST`：解释“为什么为空 + 下一步动作”。
- 加载：
  - `MUST`：使用 skeleton 或占位结构，保持版式稳定。
- 部分失败：
  - `MUST`：保留成功产物，不因部分失败回滚全部可用结果。

## 3.6 CLI 交互规范（与 Web 一致语义）
- `MUST`：CLI 输出也要体现阶段状态与结构对象变化，不只打印自由文本。
- `MUST`：错误输出包含可重试建议，格式稳定可脚本化解析。
- `SHOULD`：非交互模式输出结构化摘要（JSON/markdown 路径提示）。

## 3.7 移动端适配原则
- `MUST`：支持核心浏览与关键动作，不要求完整桌面体验对等。
- `MUST`：优先保障：
  - 查看会话状态
  - 查看假设/风险
  - 查看资产导出结果
  - 触发关键重试/确认动作
- `SHOULD`：工作台采用可切换面板（结构/对话/快照）而非硬三栏。

## 4. 视觉规范

## 4.1 字体、字号、间距、圆角、阴影、边框、留白
- 字体：
  - `MUST`：正文与代码/结构化文本字体分离。
- 字号层级：
  - `MUST`：至少有标题、小标题、正文、注释四层。
- 间距：
  - `MUST`：使用统一间距尺度（基于固定节奏，如 4/8 基线）。
- 圆角与阴影：
  - `MUST`：轻量、统一，不以阴影制造层级噪声。
- 边框：
  - `MUST`：用于分组和可交互区域识别，不能取代留白。
- 留白：
  - `MUST`：重点区域周围有足够呼吸空间，避免信息墙。

## 4.2 色彩原则（风格方向）
- `MUST`：以中性基底 + 语义色点缀。
- `MUST`：语义色仅用于状态表达，不用于随机装饰。
- `MUST NOT`：出现高饱和渐变主导业务界面。

## 4.3 图标与状态色规则
- 图标：
  - `MUST`：同语义同图标，避免一页多种含义冲突。
- 状态色：
  - info：中性/冷色
  - success：通过/完成
  - warning：风险/待确认
  - danger：失败/冲突/阻断
- 风险色和警告色：
  - `MUST`：按严重程度区分层级，不可同色同强度覆盖全部问题。

## 4.4 禁止的 UI 风格问题
- `MUST NOT`：过度花哨动画、过重拟物、玻璃化泛滥。
- `MUST NOT`：信息过密无层级、标签爆炸、色彩爆炸。
- `MUST NOT`：流程关键动作依赖多层弹窗串联。
- `MUST NOT`：仅依赖颜色区分状态（必须有文本或图标辅助）。

## 5. AI 产品专项规范

## 5.1 AI 输出区 vs 人工输入区
- `MUST`：空间上明显分离，避免混淆“系统生成”和“用户决策”。
- `MUST`：输入区显示本轮上下文摘要（你将影响哪些对象）。

## 5.2 reasoning / result / artifact / warning / action 区分
- `MUST`：每条系统输出至少可归类到以下类型之一：
  - reasoning（推理过程）
  - result（阶段结果）
  - artifact（沉淀资产）
  - warning（风险与冲突）
  - action（下一步建议动作）
- `MUST`：视觉样式与标签统一，支持筛选查看。

## 5.3 多阶段执行与可追溯性
- `MUST`：展示阶段序列、当前阶段、耗时、重试次数。
- `MUST`：每个阶段能追溯：
  - 输入
  - 执行者（engine/agent/user）
  - 输出
  - 状态
- `SHOULD`：支持“仅看失败阶段”过滤。

## 5.4 假设、风险、冲突、结论、待验证项展示
- `MUST`：分别独立列表，不混在同一消息流。
- `MUST`：每项有状态字段与来源字段。
- `MUST`：支持“从对话定位到结构项、从结构项反查对话”。

## 5.5 快照与版本差异展示
- `MUST`：快照列表至少显示版本号、时间、触发原因、核心变化计数。
- `MUST`：diff 视图至少分三段：
  - 新增
  - 修改
  - 删除
- `MUST`：对文档资产差异支持段落级或条目级比较，而非整页替换。

## 6. UI Review Checklist

## 6.1 架构与信息
- [ ] 页面是否明确体现 Challenge/Decision/Asset 三段链路。
- [ ] 会话页是否同时存在对话视图与结构视图。
- [ ] 是否存在“纯聊天壳”倾向（无结构对象区）。

## 6.2 交互与状态
- [ ] 长任务是否显示阶段化状态而非单一 loading。
- [ ] 错误/部分失败是否提供明确恢复路径。
- [ ] 重试是否具备可预期范围（全量/步骤级）。

## 6.3 视觉与可读性
- [ ] 是否遵循克制风格，避免装饰压过信息。
- [ ] 状态语义色是否一致且可读。
- [ ] 信息密度是否高但有层级，不是信息墙。

## 6.4 AI 专项
- [ ] reasoning/result/artifact/warning/action 是否可区分。
- [ ] 阶段结果是否可追溯到输入和执行者。
- [ ] 快照与版本差异是否可读可定位。

## 6.5 双端一致性
- [ ] CLI 与 Web 是否保持同一状态语义和错误语义。
- [ ] Web 的结构对象是否能在 CLI 输出中找到等价摘要。
